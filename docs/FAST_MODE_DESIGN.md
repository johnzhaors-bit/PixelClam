# PixelClam 快速验收模式设计

状态：设计冻结，计划下一开发日实施。

## 1. 目标

在不依赖程序预判“页面出现了哪些组件”、不删减 DOM 证据、不删减当前皮肤组件规范的前提下，显著减少模型调用轮数。

快速模式与现有模式并存：

- **深度模式**：DOM 作为共同证据，每个组件规范单独验收，准确率优先。
- **快速模式**：完整 DOM 作为固定前缀，把当前皮肤的全部独立组件规范按上下文容量动态装包，尽可能少轮完成，速度优先。

快速模式接受模型注意力稀释带来的漏检风险，定位是“发现多少算多少”，但不能因为程序筛选而漏掉规范。

## 2. 已确认的真实数据

以 NIV 皮肤和现有真实运行快照为例：

- 独立组件规范：64 份。
- 64 份规范合计约 1.27 MB。
- 裁剪后的模型 DOM 证据约 700 KB。
- 原始 DOM 快照约 1.36 MB。
- 裁剪 DOM + 全部组件规范约 1.97 MB，尚未包含布局规范、系统提示与输出模板。

19 条简短结构化问题通常只占几 KB。主要风险在输入上下文和请求体，不在最终问题数量。

## 3. 核心请求结构

`chat/completions` 按无状态接口处理。不能假设“第一轮只发 DOM，后续只发规范”时模型仍记得 DOM。

每一批请求在逻辑上都包含相同的固定前缀：

```text
固定系统提示
完整裁剪 DOM
统一验收说明
统一输出模板
--------------------
本批组件规范（变化部分）
批次编号与组件清单（变化部分）
```

固定内容必须始终放在前面，可变批次放在最后，最大化 Kimi 服务端前缀缓存命中。

后台记录已经出现 `cached_tokens`，说明 Kimi 网关存在自动前缀缓存。但当前没有显式 `cache: true`，也不能把缓存理解成服务器替应用永久保存会话。

## 4. 动态上下文预算

禁止写死“两批”“三批”或平均按组件数量分包。组件规范大小差异明显，例如 table、popover、select 远大于普通小组件。

每批可用容量按 token 计算：

```text
模型上下文窗口
- 固定前缀 token（系统提示 + DOM + 固定模板）
- 预留输出 token
- 协议及消息包装开销
- 安全余量
= 本批组件规范可用 token
```

建议初始安全余量为上下文窗口的 15%，并允许配置：

```json
{
  "fastMode": {
    "contextWindowTokens": 131072,
    "reservedOutputTokens": 6000,
    "safetyRatio": 0.15,
    "maxIssuesPerBatch": 30
  }
}
```

`contextWindowTokens` 必须由模型配置提供默认值，并允许用户修改，因为第三方网关可能对同名模型设置不同限制。

## 5. Token 估算与校准

实现两级估算：

1. **请求前估算**：使用可用 tokenizer；若模型 tokenizer 不可用，采用 UTF-8 字节数/字符类别的保守估算并额外保留安全空间。
2. **首轮实测校准**：读取响应 `usage.prompt_tokens`，比较实测值和估算值，校准剩余批次的装包上限。

规范按文件真实 token 数进行顺序装箱，不按文件数量平均分割。每个组件 JSON 必须保持完整，不能把同一个组件规范从中间切开。

## 6. 自适应失败处理

快速模式必须处理以下情况：

- 上下文长度超限。
- HTTP 请求体过大。
- 请求超时或连接中断。
- 模型返回 JSON 被截断。
- 模型声称收到的规范数少于本批实际数量。

处理策略：

1. 当前批次发生容量类错误时，将该批规范按 token 总量二分后重试。
2. 仍失败则继续二分，直到单组件批次。
3. 单组件仍失败时记录明确错误，不把它伪装成“0 条问题”。
4. JSON 输出截断时，先尝试一次短 JSON 修复；仍失败则缩小该批并重跑。
5. 网络错误采用有限次数指数退避，不无限等待。

如果固定前缀本身已超过安全上下文容量，应停止快速模式并明确提示“DOM 本身过大”。后续可增加机械 DOM 压缩或区域分片，但不得静默删除组件规范。

## 7. 模型输出契约

每批只返回短结构化 JSON，不输出长篇解释：

```json
{
  "batch": {
    "index": 1,
    "total": 3,
    "receivedStandardCount": 18,
    "receivedComponents": ["button", "input", "select"],
    "lastReceivedComponent": "select",
    "domReceived": true
  },
  "issues": [
    {
      "component": "button",
      "location": "查询区，代码位置（#query-button）",
      "problem": "当前高度40px，应该32px；当前圆角10px，应该3px",
      "severity": "high"
    }
  ],
  "summary": "本批发现2条问题"
}
```

程序必须核对：

- `domReceived` 为 true。
- `receivedStandardCount` 等于本批规范数。
- `receivedComponents` 覆盖本批组件清单。
- `lastReceivedComponent` 与本批最后一个组件一致。

确认失败时不能直接接受“0条问题”，应缩小批次重试或标记验收不完整。

## 8. 报告合并

所有批次结果由本地程序合并，不再额外调用模型做全文总结：

- 合并 issues。
- 按组件、位置、问题内容去重。
- 保留问题来源批次。
- 汇总成功、失败、重试和未确认组件。
- 使用现有评分与 HTML 报告渲染流程。

报告中增加快速模式诊断信息：

- 总批次数和实际模型调用次数。
- 每批组件数、输入/输出 token。
- `cached_tokens` 和缓存命中率。
- 上下文估算值与实测值。
- 重试、二分及未完成批次。
- 64 份规范是否全部被模型确认接收。

## 9. 界面与进度

检测模式提供：

- `深度检测（准确优先）`
- `快速检测（速度优先）`

快速模式进度至少显示：

1. 读取 DOM 与当前皮肤规范。
2. 估算上下文并生成动态批次。
3. 当前批次 `n/N`、本批组件数与预计 token。
4. 模型连接、缓存命中及发现问题数。
5. 失败拆包重试提示。
6. 合并报告。

## 10. 缓存原则

- 固定前缀的字节内容和顺序必须完全一致。
- 不在 DOM 前插入批次编号、组件名、时间戳或随机请求 ID。
- 批次变化内容全部置于固定前缀之后。
- 每批仍要逻辑携带 DOM；缓存是服务端优化，不是会话记忆。
- 缓存未命中不影响正确性，只影响速度与费用。

## 12. 验收标准

- 不进行组件出现性盘点，不因程序判断删除规范。
- 当前皮肤全部独立组件规范均进入某一批，且文件保持完整。
- 分包数量由上下文预算动态产生。
- 容量超限能自动缩批重试。
- 模型确认收到的组件集合可核对。
- 多批结果可稳定合并为一份报告。
- 快速模式明显少于深度模式调用轮数。
- 深度模式行为保持不变。
